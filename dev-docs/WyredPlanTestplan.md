# Wyred Testplan Plan — `.testplan.json` + `wyred-bench` (WorkflowDesign §3.3)

*Phased plan elaborating [WyredWorkflowDesign.md](./WyredWorkflowDesign.md)
§3.3 (test definition — "the moat stage"). Each phase is a shippable
milestone; each step is one goal budgeted to an aspirational < 500 LOC.
Per step: repo / ~LOC / model (opus-4.8 for mechanical builds; fable for
vocabulary + contract design) / mechanical acceptance. This document
proposes — it changes no contract bytes and commits nothing by itself;
contract changes land only via the single-writer flow (accepted proposal →
wyred-contract version bump).*

## 0. Invariants (every step, non-negotiable)

- **Opt-in emission.** `<name>.testplan.json` is emitted **only when test
  declarations exist** on the artifact. An intent with zero test
  declarations emits exactly what it emits today. Mechanical guard on
  *every* step's acceptance: a fresh emit of `wyred-examples/corpus` is
  byte-identical to `wyred-contract/goldens/ga019` (no new files for
  existing intents, no changed bytes), and `wyred-examples/run_gate.py`
  exits 0 end-to-end. Goldens are never regenerated by this plan —
  regeneration is a contract event, and this plan requires none.
- **Ranges are new — and every one is a ratification item.** The
  engine/harness voltage model today is a rigid scalar with a float-noise
  absorber: `VTOL = 0.05` in `wyred/src/wyred/concepts.py` and
  `resolve.py`, `_VTOL = 0.05` in `wyred-harness/harness/erc.py`,
  `intent_oracle.py`, `spec_satisfaction.py` — commented "absorbs float
  noise only, never a real tolerance". The testplan vocabulary introduces
  **real acceptance ranges** for the first time (WorkflowDesign §3.3/§4:
  "the first deliberate crack in the rigid-scalar model"). Every place
  that scalar model is deliberately loosened is flagged **RATIFY-n**
  inline below and collected in §6; none lands without a recorded stance
  in `DecisionLog.md`. The design-time `VTOL` constants themselves are
  **untouched** by this plan.
- **wyred-bench is a NEW member repo** (currently listed under "Planned,
  not created" in the root README). It is created with `gwz repo create`
  and fenced by its CLAUDE.md: **depends on wyred-contract only** —
  schemas, goldens, and committed fixtures; it never imports `wyred`,
  `wyred-harness`, or `wyred-audit`; it meets them only at artifacts on
  disk (the star topology, depth 1).
- **Contract via single-writer.** The `.testplan.json` shape, the
  measurement-record shape, and the comparator's verdict codes are
  contract vocabulary. They enter `wyred-contract` only through the
  Step 1.1 proposal, accepted and recorded in DecisionLog, with a
  contract version bump. No repo edits the contract as a side effect of
  its feature work.
- **No commits from planning.** This plan directs future sessions; the
  session that wrote it commits nothing.

## 1. Phase 1 — vocabulary + emitter (`wyred`)

**Milestone:** the engine emits a derived, deterministic, provenance-carrying
`.testplan.json` for any artifact whose author declared tests — and emits
nothing new for anyone else. Run_gate green throughout.

### Step 1.1 — Test-intent semantics + `.testplan.json` contract proposal

- **Repo:** `wyred-wz/dev-docs` (proposal doc, e.g.
  `ProposalTestplanContract.md`); lands in `wyred-contract`
  (EMIT_CONTRACT Part E + version bump) only after acceptance.
- **~LOC:** doc, not code. **Model: fable** (vocabulary + contract design).
- **Goal:** one accepted document defining the test vocabulary, the
  `.testplan.json` shape, and (v1-draft) the measurement-record shape and
  verdict codes, so Phases 1–3 build against a fixed seam.

Contents the proposal must settle:

1. **Vocabulary** (marker-declaration form, §3.3 signatures):
   `expect_rail(tp, volts, tol=)`, `expect_i2c_scan(bus, addrs=)`,
   `expect_current(rail, max_ma=, state=)`,
   `expect_signal(tp, freq=, duty=)`. `late(...)` must work in every
   argument position (the injection cascade); check identity is minted
   from the declaring attribute path (law 8 — `bench.rail_3v3`, never an
   author-written id).
2. **Testpoint binding to pinmap entries.** The `tp`/`rail`/`bus`
   references are L1 vocabulary (demand ids, rail names, bus names —
   never refdes). The emitter resolves each check to concrete probe
   points from the **pinmap's components**: the Watchy corpus already
   models this — `DebugTaps` (`wyred-examples/corpus/watchy_v1.py`)
   realizes as `kind="test_point"` components TP1–TP7 with nets
   (`+3V3`→TP4, `GND`→TP5, `I2C0_SCL/SDA`→TP6/TP7,
   `debug.prog.tx/rx`→TP1/TP2 in
   `wyred-contract/goldens/ga019/watchy_v1.pinmap.json`). Decide:
   testpoint-ness is *inferred* from realized `kind=="test_point"`
   components (keeps L1 untouched) vs *declared* as a demand attr —
   recommend inference, with a structured emit-time failure
   (`TESTPLAN_UNPROBEABLE`) when a check's target has no probeable
   entry (no silent defaults, law 10).
3. **Where the declarations live on disk.** Constraint triangle: (i)
   existing goldens byte-identical, (ii) no `wyred-harness`/`schema_l1`
   change in Phase 1, (iii) `wyred.rebuild` from-primaries honesty must
   cover the testplan (secondaries are pure functions of on-disk
   inputs). **Recommended:** the testplan artifact carries its own
   `declarations` block (authored content) plus a `checks` block
   (derived), so `checks` is re-derivable from
   (`declarations`, records, pinmap) and `l1.json` never changes.
   Alternative — an optional `"tests"` key in the L1 doc — is legal but
   drags a harness `schema_l1` tolerance change into scope; if chosen,
   that harness step must be added explicitly, not smuggled.
4. **Tolerance semantics** — the ranges. Each of these is a deliberate
   loosening of the rigid ±0.05 V scalar model and a **ratification
   item** (full list §6): interval form and defaults for `expect_rail`
   (**RATIFY-1**), derivation of nominal volts from the L1 rail
   declaration (**RATIFY-2**), the VTOL firewall (**RATIFY-3**),
   one-sided bounds + operating `state=` for `expect_current`
   (**RATIFY-4**), per-quantity tolerance types for `expect_signal`
   (**RATIFY-5**), set semantics for `expect_i2c_scan` (**RATIFY-6**),
   boundary inclusivity + canonical number formatting (**RATIFY-7**).
5. **Provenance per check** (§3.3: "which declaration demanded it").
   Every emitted check carries: the declaration id that demanded it, and
   the derivation inputs — rail/bus/demand from the L1 doc, expected
   addresses from records (e.g. `i2c_addr` 0x18 for `accel` on `I2C0`),
   probe points `{refdes, pad, net}` from the pinmap. The testplan is
   stamped `(series, {lock_group: version})` like every other artifact,
   so a measurement is always attributable to a specific frozen pin-map.
6. **Self-containment for contract-only consumers.** wyred-bench reads
   the testplan (plus, where needed, the pinmap — both contract-defined);
   the testplan must therefore embed resolved probe points, expected
   values, and ranges — a bench card must be derivable without the
   engine.
7. **Measurement record + verdict codes (v1-draft).** Shape of
   `<name>.measurements.json` (per check id: measured value(s), unit,
   instrument/operator note) and the comparator's structured codes
   (see Step 2.2). Drafted here so Phase 2 has a seam; final
   ratification at 2.2 with the fixtures in hand.

- **Mechanical acceptance:** the proposal contains a complete worked
  example for `watchy_v1` derived by hand from the committed goldens —
  every net, refdes, address, and node in the example must exist in
  `watchy_v1.pinmap.json` / `watchy_v1.records.json` (checkable by
  grep/jq against the goldens); the example validates against the JSON
  shape given in the proposal; all seven RATIFY items carry a recorded
  stance; acceptance recorded in `DecisionLog.md` before any code step
  lands contract-shaped bytes.

### Step 1.2 — Marker declarations + elaboration

- **Repo:** `wyred`. **~LOC:** ~250. **Model: opus-4.8.**
- **Goal:** the four `expect_*` marker declarations exist as `Decl`
  subclasses in `core.py` (the `ParamDecl`/`DemandDecl` pattern:
  creation-order harvested, MRO-merged, zero-arg safe) and the engine
  elaborates them into the declaration record chosen in 1.1, with
  structured load errors for bad references
  (`TEST_UNKNOWN_RAIL`, `TEST_UNKNOWN_BUS`, `TEST_UNKNOWN_DEMAND`,
  `TEST_BAD_TOLERANCE` — the `ModellerError` channel, law 10).
- Scope guard: no emitter work here (that is 1.3); elaboration produces
  the in-memory/declaration form only. `late(...)` resolution reuses
  `resolve_value`; check ids are dotted instance paths.
- **Mechanical acceptance:** fresh emit of the untouched corpus
  byte-identical to goldens; `run_gate.py` PASS; law-2 sweep still passes
  (every module carrying test decls instantiates with zero args); a
  scratch module (test-local, not corpus) with all four decl kinds
  elaborates twice byte-identically; each new error code has a unit test
  that provokes exactly it.

### Step 1.3 — Emitter: checks derived from decls + records + pinmap

- **Repo:** `wyred`. **~LOC:** ~250. **Model: opus-4.8.**
- **Goal:** `paths.py` gains `build_testplan(name, decls, records,
  pinmap)` (the `build_bom`/`build_pinmap`/`build_records` sibling);
  `emit.py` writes `<name>.testplan.json` **iff** declarations are
  non-empty, double-resolved and byte-compared into the existing
  `paths_det` determinism check; `rebuild.py` re-derives the `checks`
  block from on-disk inputs and byte-compares (from-primaries honesty —
  the audit picks this up through its existing `REBUILD_FROM_PRIMARIES`
  subprocess stage, no `wyred-audit` change).
- Derivation rules (per 1.1): rail checks bind to `test_point`
  components on the rail net plus a ground reference point; i2c-scan
  expected addresses default from the L1/records bus attachments
  (say-only-the-non-default: `addrs=` overrides); every check emits
  provenance + probe points; an unprobeable check is
  `TESTPLAN_UNPROBEABLE` at emit, never a silently thinner testplan.
- **Mechanical acceptance:** untouched corpus emits **zero**
  `*.testplan.json` files and stays byte-identical to goldens;
  `run_gate.py` PASS; a fixture decl-set over the watchy golden inputs
  reproduces the 1.1 worked example byte-for-byte; double-emit
  determinism enforced by the emit loop (a deliberate nondeterminism
  injection in a test fixture must trip it); `rebuild --all` over a tree
  containing a testplan verifies it and over a tree without one is
  unchanged.

### Step 1.4 — Probe corpus (new, not golden)

- **Repo:** `wyred-examples`. **~LOC:** ~150. **Model: opus-4.8.**
- **Goal:** a new corpus file (e.g. `corpus/watchy_v1_bench.py`)
  declaring tests **over an existing intent** — a new intent root
  reusing the Watchy modules (subclass or recomposition; new artifact
  name `watchy_v1_bench`) that declares: `expect_rail` on `+3V3`
  (binds TP4/TP5), `expect_i2c_scan("I2C0")` (derived `[0x18]`, probes
  TP6/TP7), `expect_signal` on a debug tap, and `expect_current` on
  `+BATT` with a declared `state` (no testpoint needed — probe method is
  a bench-card matter). Where a vocabulary item is not honestly
  groundable on Watchy, it is exercised in 2.2's comparator fixtures
  instead — no fabricated testpoints.
- Its emitted artifacts (including the testplan) land in `out/` like any
  corpus emit and are **not** added to `wyred-contract/goldens`
  (goldens change only by contract event; this artifact is a probe, not
  a normative fixture).
- **Mechanical acceptance:** `run_gate.py` PASS over the enlarged corpus
  (the new intent is declared-clean, so gate + audit + determinism must
  all hold on it, including the testplan's rebuild honesty); the
  pre-existing artifact set in `out/` remains byte-identical to goldens;
  exactly one `*.testplan.json` exists in `out/` and it round-trips
  the 1.1 schema.

## 2. Phase 2 — `wyred-bench` member + consumers

**Milestone:** given only committed contract artifacts, a human gets an
ordered bench card, and a filled-in measurement record gets a mechanical
verdict — the oracle stack's first step into physics.

### Step 2.1 — Create wyred-bench + bench-card generator

- **Repo:** workspace root + new `wyred-bench`. **~LOC:** ~200.
  **Model: opus-4.8.**
- **Goal (a) — the member exists:** `gwz repo create` for `wyred-bench`
  (owebeeone remote, registered in `gwz.conf/gwz.yml` like the nine
  existing members); `CLAUDE.md` fence: *"Depends on wyred-contract only
  (testplan / pinmap / measurement schemas, goldens, fixtures). Never
  imports wyred, wyred-harness, or wyred-audit; meets them at artifacts
  on disk. Python, stdlib-only."* Root `README.md`: move `wyred-bench`
  from "Planned, not created" into the member table
  (`depends on: contract`).
- **Goal (b) — bench card:** `python -m wyred_bench.card --testplan
  <X>.testplan.json --out <X>.benchcard.md` renders the testplan as an
  ordered human-readable check card: documented ordering policy
  (power-off/continuity → power-on rails → current → buses → signals),
  per check: id, expected value with its range, probe points
  (TP refdes + net), instrument hint, provenance, and the testplan's
  `(series, lock versions)` stamp in the header.
- Fixtures: a committed testplan fixture matching the 1.1 worked example
  (hand-verified against the contract, since goldens carry no testplan).
- **Mechanical acceptance:** generator run twice on the fixture yields
  byte-identical markdown; snapshot test committed; every check appears
  exactly once and in the documented order; `grep`-check that no source
  file imports anything outside stdlib (the fence, mechanically).

### Step 2.2 — Measurement-record schema + comparator (THE oracle)

- **Repo:** `wyred-bench` (schema ratified into `wyred-contract` via the
  1.1 proposal's v1-draft — single-writer). **~LOC:** ~250.
  **Model: opus-4.8.**
- **Goal:** `<name>.measurements.json` (per check id: measured value(s),
  unit, note) and `python -m wyred_bench.compare --testplan T
  --measurements M` producing a structured verdict artifact + nonzero
  exit on any failure. This comparator **is** the oracle §3.3 promises:
  a measured board vs the testplan, mechanical, gate-red on
  disagreement. Codes (contract vocabulary): `RAIL_OUT_OF_RANGE`,
  `I2C_SCAN_MISSING_ADDR`, `I2C_SCAN_UNEXPECTED_ADDR`,
  `CURRENT_EXCEEDED`, `SIGNAL_OUT_OF_RANGE`, `CHECK_UNMEASURED`,
  `MEASUREMENT_UNKNOWN_CHECK`, `UNIT_MISMATCH`, `STATE_MISMATCH`.
  An unmeasured check is a failure, not an omission (no silent
  defaults extends into physics).
- Fixtures with **simulated measurements, including failing ones**: an
  all-pass set; one fixture per verdict code; boundary fixtures with
  values exactly at range min/max (these *encode* the RATIFY-7 stance);
  a stale-stamp fixture (measurements taken against a different
  `(series, lock versions)` stamp must be refused, not compared).
- **Mechanical acceptance:** every verdict code is provoked by at least
  one committed fixture and asserted by a test; all-pass fixture exits
  0, every failing fixture exits nonzero naming exactly its code;
  comparator output is byte-deterministic across runs; boundary
  fixtures pass/fail per the ratified interval semantics.

## 3. Phase 3 — firmware self-test scaffolding

### Step 3.1 — Self-test stub generator (template-driven, honest)

- **Repo:** `wyred-bench`. **~LOC:** ~350. **Model: opus-4.8.**
- **Goal:** a generator emitting firmware self-test **stubs** against the
  pinmap (the firmware-facing artifact was built for exactly this):
  from `testplan + pinmap`, emit (a) a C module and (b) a
  MicroPython-style module that iterate the testplan's checks — rail
  reads as ADC checks, bus checks as I2C scans — and write results in
  the 2.2 measurement-record shape, so the firmware self-test's output
  is scored by the same comparator (one oracle, two probe routes).
- **Template-driven and honest about what's stubbed:** hardware access
  is emitted as extern/abstract hooks (`adc_read_mv(chan)`,
  `i2c_scan(bus)`); anything not derivable from the artifacts (ADC
  channel-to-pad mapping, MCU pin muxing) is a generated `TODO` table
  plus a machine-readable `NOT_IMPLEMENTED` manifest listing every hook
  left abstract — the generator never fabricates a register map. Each
  generated check carries its testplan check id + provenance as a
  comment.
- **Mechanical acceptance:** generated C passes `cc -fsyntax-only`;
  generated Python passes `py_compile`; every testplan check appears
  exactly once in each target; snapshot tests over the 2.1 fixture; a
  simulated run of the Python stub with injected fake readings produces
  a `measurements.json` that the 2.2 comparator scores green, and with
  one injected out-of-range reading, red with the right code; the
  `NOT_IMPLEMENTED` manifest is non-empty and enumerated in the test
  (the honesty is itself asserted).

## 4. Phase 4 — physical loop (explicitly deferred)

Deferred to the tracer-bullet board (an open decision in
WyredWorkflowDesign §6). When a fabbed board exists: the measured board
is the **final exogenous denotation** — bench or firmware measurements
land as a measurement record for a specific board serial against a
specific testplan stamp, the 2.2 comparator scores it, and the run is
**gate-wired exactly like the board-agreement probes** in
`wyred-examples/run_gate.py`: content-based readiness check, the
ground-truth (board serial + testplan `(series, lock versions)` stamp)
pinned on stdout before the probe runs, a loud SKIP banner naming
exactly what was not verified when no measurement record is present —
never a silent pass — and a failed check as gate-red, the same as any
other disagreement. No steps are planned until the board exists; this
paragraph is the record that the deferral is deliberate.

## 5. Coupling & parallelism map

- **1.1 is the foundation** — it blocks everything (vocabulary for
  1.2/1.3/1.4, schemas for 2.1/2.2).
- After 1.1 acceptance: **1.2 → 1.3 → 1.4** are sequential within
  `wyred`/`wyred-examples`; **2.1 and 2.2 run in parallel with all of
  them** — wyred-bench builds against the contract's committed shapes
  and fixtures, not the engine (the star-topology payoff: the seam is
  the proposal, not the code).
- **3.1** needs 1.1 (testplan shape) + 2.2 (measurement record); it does
  not need Phase 1's engine steps to have landed.
- Phase 4 needs a board, 1.3 (a real emitted testplan), and 2.2 (the
  comparator); nothing in Phases 1–3 depends on it.

## 6. Ratification items (the tolerance semantics)

Every deliberate loosening of the rigid ±0.05 V scalar model
(`VTOL`/`_VTOL = 0.05`, float-noise-only, in `wyred/src/wyred/concepts.py`,
`wyred/src/wyred/resolve.py`, `wyred-harness/harness/erc.py`,
`intent_oracle.py`, `spec_satisfaction.py`). Each needs a recorded stance
in `DecisionLog.md` at 1.1 acceptance; none is a silent default.

- **RATIFY-1 — `expect_rail` tolerance form and default.** `tol=`
  replaces scalar equality with a closed acceptance interval
  (`[volts − tol, volts + tol]`, or explicit min/max for asymmetric
  bands). Decide: absolute volts vs percent; and whether an omitted
  `tol` is a load error or a declared vocabulary default (e.g. ±5 %) —
  it must NOT silently inherit 0.05 V.
- **RATIFY-2 — derived nominals.** When `expect_rail`'s `volts` is
  omitted, the nominal derives from the L1 rail declaration
  (say-only-the-non-default) — which turns a design-time rigid scalar
  (`rail("+3V3", 3.3)`) into the center of a measurement range by
  derivation. Ratify that this derivation is legal and one-way.
- **RATIFY-3 — the VTOL firewall.** Design-time voltage compatibility
  (`VTOL`/`_VTOL`) stays a float-noise absorber and is neither widened
  nor reused as a measurement tolerance; the two numbers share a unit
  but not a meaning. Any future unification is its own contract event.
- **RATIFY-4 — one-sided bounds and operating states.**
  `expect_current(rail, max_ma=, state=)` introduces (a) the
  vocabulary's first inequality check (≤ max, no lower bound) and (b)
  `state=` — expected values conditional on a board operating state
  ("sleep", "active"), a dimension with no L1 counterpart. Ratify both
  the one-sidedness and the state vocabulary (free strings vs enum).
- **RATIFY-5 — per-quantity tolerance types.** `expect_signal(tp,
  freq=, duty=)` needs typed ranges per physical quantity: frequency in
  ppm (crystals) vs percent (RC clocks), duty in absolute percentage
  points — units and default bands are policy, not derivable from
  records.
- **RATIFY-6 — set semantics for `expect_i2c_scan`.** Expected-address
  matching: exact set vs subset ("at least these"). An unexpected extra
  address found on the bus — failure or warning? (Recommended: exact
  set, extra address fails — a rogue device is a disagreement, not a
  freebie.)
- **RATIFY-7 — boundary inclusivity + numeric canonicalization.** A
  measured value exactly at a range bound: pass (closed interval) or
  fail? And the canonical float formatting rule for testplan and
  measurement JSON, so the byte-determinism discipline (double-emit
  compares, rebuild honesty) survives the arrival of ranges and
  physical measurements.
